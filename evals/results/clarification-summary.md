# TraceForge 澄清评测：2026-09-24

最终完整报告：[clarification-20260924-105353.json](clarification-20260924-105353.json)。模型为 `deepseek-flash`，使用 TraceForge 现有 Web 模型配置。20 个中文用例中，10 个标为“必须向用户提问”，10 个标为“不应提问”；评测的是 TaskBrief Hook 与其生成的问题，没有运行完整 Agent 工具链。

| 指标 | 结果 |
| --- | ---: |
| 决策正确 | 19/20 |
| 必须提问且实际提问（TP） | 10 |
| 不必提问却提问（FP） | 1 |
| 必须提问却未提问（FN） | 0 |
| 不必提问且未提问（TN） | 9 |
| 用例级提问 precision / recall / F1 | 0.909 / 1.000 / 0.952 |
| 已模拟回答后转入执行 | 3/3 |

唯一误判是 `specified_deployment`：用户只要求添加面向 Linux、监听 8000 端口的 Docker Compose *部署说明*，模型仍追问是否还要新增 Dockerfile 和编排文件。该问题把“写说明”扩大成了尚未请求的交付物。

人工检查 10 个必须提问的样本：每例最终都问到了标注的核心缺口，但共生成 18 个问题，其中有些可在用户回答核心问题或仓库调查后再决定。7 例的全部问题为英文，尽管用户输入为中文；这影响中文优先界面的体验。问题语义没有使用独立 LLM judge 打分，因此这里不报告逐条问题 precision。

早期两轮探索性运行各为 15/20，失败样本不同；当时受控调查证据配置也在调整，因此不能视为同条件的稳定性复测。它们暴露了一个机制问题：[TaskBriefHook](../../backend/traceforge/task_brief.py) 只要发现任意可从仓库调查的缺口，就先进入 `discovering`，即使同一份结果还有明确的、必须由用户回答的阻塞项。最终完整运行中，这类样本没有造成漏问，但此前出现过延后提问。能力询问“你能帮我查看这个项目的代码吗？”在早期两轮误问，最终一轮正确，说明模型路由仍有波动。

限制：本次只测澄清门控和回答复检；没有验证真实工具调查、UI 问题卡片、用户交互耗时或最终代码任务完成率。需要这些指标时，应在隔离工作区对完整 Agent Loop 做端到端评测。
